NetHealth

How this app was built — a conversational walkthrough

Build Tutorial

NetHealth was built the way every app here is: one idea, then a series of small refinements. Here is the journey, prompt by prompt — including the wrong turn that taught us the most.

1

The idea

I would like a new project — a macOS app that shows me a beautiful picture of my internet health. It should ping my Starlink router regularly, and a known public website, and show me the ping time graphically and gorgeously in a resizeable window.

We picked three things to watch — the Starlink router (192.168.1.1), the dish itself (192.168.100.1), and Cloudflare (1.1.1.1) as a public anchor — and an aurora ribbon aesthetic: flowing translucent gradients on a deep dark background.

solarsystem is a good one to look at!

So the project was scaffolded in the house style — hand-authored project.pbxproj, MVVM, zero dependencies — modelled on the SolarSystem project's macOS target.

2

Write, build, test — hands-off

please write, build and test — you don't need my permissions for that.

The model layer (PingSample, HealthState, TargetHealth), an actor ping service, the view model's 1 Hz probe loop, and the SwiftUI dashboard all went in, and the project built clean on the first real compile after a couple of small fixes.

3

Testing without a screen

you can use command line args to test without having to screengrab the graphics to see if it is working.

Exactly right. A --selftest launch argument measures each target once and prints the result, and a --netdiag mode reports the raw result and errno of every socket step. That let the whole networking path be verified head-less:

./run-macos.sh Debug --selftest
4

The wrong turn that taught us the most

The first design used real ICMP echo (actual ping). It built and ran — and reported every target, even loopback, as unreachable. The shell could ping fine, so it wasn't the network. --netdiag found the culprit:

ICMP socket(): ok fd=3
raw: sendto -> 16
raw: recv -> -1 errno=1 (Operation not permitted)
TCPPinger.ping(1.1.1.1:443): 30.74 ms
Aha: the macOS App Sandbox lets you create and send on an unprivileged ICMP datagram socket, but denies the inbound echo reply with EPERM. So we measure latency by TCP connect time instead — one round trip, a close proxy for ICMP RTT — and fall back to it automatically the instant ICMP is refused.

With that, the self-test lit up green against real hardware (the via column — added later — names the winning probe):

  [OK]   Router      192.168.1.1          4.5 ms  via TCP
  [OK]   Dish        192.168.100.1        2.6 ms  via TCP
  [OK]   Cloudflare  1.1.1.1             25.0 ms  via TCP
3/3 targets reachable
looks pretty good — and works!
5

Making it move

Do you think we can animate the charts between the timed steps? That would look smoother.

The data only changes once a second, so the ribbon visibly stepped. A TimelineView 60 Hz clock was wired in to interpolate between samples, plus eased vertical re-scaling so spikes don't snap.

I think the graph is just compressing as time goes on, rather than scrolling through time. I think scrolling through time might be better, don't you?

Spot on. The fix was to position each point by its real age (now − sample.date) across a fixed 90-second window, so the ribbon scrolls continuously and old data slides off the left edge.

6

Polish: legibility and smoothness

larger y axis text please, my eyesight isn't good enough!

The Y-axis labels were bumped to 15 pt semibold, brighter and left-aligned.

it does seem to stutter often when the data updates, looks like it shifts slightly one way then the other.

A real artifact: with age-based positioning the newest point drifts left for a second, then a fresh point pops in at the right edge — a ~7 px right-then-left sawtooth. The fix was to pin the leading edge: hold the latest value out to x = width so the trace only ever glides left. We also gave the auto-scale hysteresis so it can't flip-flop between ranges.

ooh seems much better now — the smoothness.
7

Leave the dish alone

the dish may have crashed because it was being poked. So let's not do that!
no the normal icmp and tcp connect probe are fine — let's not try and access its api

The dish had gone unresponsive while being probed once a second, and the Phase 2 plan was to talk to its gRPC API on port 9200. The catch: that same SpaceX.API.Device.Device/Handle endpoint which serves telemetry also accepts reboot and stow. So port 9200 was dropped from the dish's probe list entirely — the dish is now timed with a gentle TCP connect on its web ports only, and Phase 2's gRPC plan was shelved.

is there any doc out there about this kind of issue with starlink dishes?

No smoking-gun bug for a bare TCP poke, but the community starlink-grpc-tools independently warns about polling the dish too often and ships explicit “dish reboot detected” handling — enough to justify keeping NetHealth a strictly passive monitor.

8

Show the measurement path

let's have the display show whether icmp or tcp is being successful.

Since ICMP is tried first and silently falls through to TCP, it wasn't obvious which path was actually live. The probe now returns a Reading(rtt, method); the method rides along in each PingSample and shows as a small badge on every stat card — a muted TCP, or a green ICMP when real echo works. --selftest prints it too. On a sandboxed build every card reads TCP, making the sandbox/ICMP story self-evident at a glance.

9

Make it work on any network, not just Starlink

now I want to extend it slightly so it handles networks other than a local starlink setup. Like right now, connected via wifi to my fiber router… update the app to handle changing router address, and grey out / omit the starlink section if we can't reach the starlink dish.

Three changes, and the app stopped being Starlink-specific. The Router target now follows the real default gateway — a new Gateway helper reads the kernel routing table via sysctl(NET_RT_DUMP) (the in-process equivalent of route -n get default, and sandbox-safe), so on the fiber LAN it lit up at 192.168.108.1 instead of the hard-coded Starlink 192.168.1.1. The dish became an optional target: an optional target that has never answered is omitted entirely — from the cards, the graph ribbons, and the overall-health tint — so the missing dish no longer painted the whole window "Offline". And a subtle but important fix: a connection-refused RST now counts as reachable, since it's a complete round trip from a host that's simply got no open web port — which is exactly how a bare fiber gateway reads as a healthy local hop.

The owner chose omit over grey-out for the absent dish, so on fiber the dashboard cleanly shows two cards (Router + Cloudflare) and two ribbons, the header reading a calm green "Excellent". --selftest confirmed it, printing the detected gateway and reporting the dish as [--] not present (optional) rather than a failure:

NetHealth self-test — measuring 3 targets
  default gateway: 192.168.108.1
  [OK]   Router      192.168.108.1        2.8 ms  via TCP
  [--]   Dish        192.168.100.1    not present (optional)
  [OK]   Cloudflare  1.1.1.1             10.2 ms  via TCP
2/3 targets reachable
10

Every connection at once — and a bandwidth test

On this Mac I have wifi connecting to a fibre broadband router capable of 5Gb/sec, and wired ethernet connected to a starlink router/dish. I'd like to extend the app to show all current network connections, rather than just the default. And also include a periodic bandwidth test. Stacked charts would be nice — one for each distinct connection. How does that sound?

A look at the routing table showed both links live at once: Ethernet (en0) → Starlink as the primary default route, and Wi-Fi (en1) → fibre as a second, RTF_IFSCOPE-scoped default route. That scoping is the crux — ordinary sockets only ever use the primary, so to see the fibre at all every probe has to be pinned to its interface.

perhaps once per minute for now. upload too. and yes please — take a snapshot first, and go ahead.

After snapshotting to nethealth copy, Gateway learned to return every default route with its interface index and a primary flag; ConnectionDiscovery merges those with NWPathMonitor's interface types into one NetworkConnection per link, each with its own Router, optional Dish and Cloudflare targets. TCPPinger binds each socket with IP_BOUND_IF, and the self-test proved it: Cloudflare read 24.5 ms via Starlink and 11.4 ms via fibre in the same run, with the dish answering only on the Ethernet link.

The bandwidth test talks to Cloudflare's __down/__up endpoints. URLSession can't be pinned to an interface, so it's HTTP/1.1 hand-rolled over NWConnection with requiredInterface. Two probes with curl shaped the design: a single stream only reached ~170 Mbps even on the fibre (so: six parallel streams), and requests over 100 MB get a 403 (so: split the byte cap across streams). Each direction stops at 4 s or 120 MB ↓ / 40 MB ↑.

NetHealth speed test — 2 connection(s), 6 streams, ≤4s / ≤120 MB down, ≤40 MB up
  Ethernet  en0  gw 192.168.1.1  (primary)
    ↓ download     326.6 Mbps    120.0 MB in 3.3s
    ↑ upload        24.5 Mbps     12.6 MB in 4.4s
  Wi-Fi  en1  gw 192.168.108.1
    ↓ download     156.1 Mbps     75.9 MB in 4.2s
    ↑ upload       101.6 Mbps     40.0 MB in 2.5s

Parallel curl over en1 agreed — the Mac's Wi-Fi hop, not the 5 Gb/s fibre, is the limit. The window now stacks a panel per connection (badged PRIMARY / STARLINK), each with its own ribbon, stat cards and a Bandwidth card with live Mbps and a sparkline. Test spans are shaded on the graph, which made bufferbloat visible straight away: Wi-Fi latency to Cloudflare climbed from ~10 ms to over 100 ms during the download.

Two things surfaced on the first live run. Cloudflare answered one Wi-Fi download with HTTP 429 — once a minute is enthusiastic — so a rate-limited link now backs off 5 → 30 minutes and keeps showing its last good reading. And the fibre router briefly dropped most probes right after a burst of back-to-back tests; a new --watch mode (the GUI's concurrent probe loop, logged per tick) showed the probe logic was sound and the router recovered on its own.

11

Lining up the cards, and getting downloads back

let's line the number panels up, so if there's no dish entry, just leave a gap. And neither connection is showing download numbers
yes one bandwidth test every 5 mins is fine. Perhaps reduce the amount of data per test too?

The missing downloads weren't the same 429 as before. A single 1 MB curl got a 200 while the app's 20 MB requests failed, and probing sizes found the line: after all that testing, Cloudflare answered 429 to any single download of 10 MB or more, but happily served a dozen back-to-back 5 MB requests on one connection. So each download stream now loops 4 MB keep-alive requests, reading Content-Length to know when to ask for the next. The default schedule became every 5 minutes, and the per-test caps dropped from 120/40 MB to 40 MB ↓ / 15 MB ↑ with a 3 s limit — at most ~55 MB per link per test, and still ~300 Mbps on Starlink and ~140 Mbps on the fibre Wi-Fi.

The cards now sit in fixed Router · Dish · Cloudflare · Bandwidth slots so the two panels line up, with a gap where the Wi-Fi link has no dish. The first try hid the Starlink dish too: the panel only observed its connection, so it never noticed the dish's everReachable flip. A small CardSlot view that observes its own target fixed it.

12

Every ten minutes, and when did we test?

let's run the bandwidth test every 10 minutes, to minimize data even more. Let's make sure the first test is soon after app start though. Let's put a timestamp of when we tested in each bandwidth chart.

A new Every 10 min option became the default, halving the worst case to ~330 MB per link per hour. The first test still fires about 5 seconds after launch, and now it won't silently slip a whole interval if the links (and the NWInterface handles that pin each test) haven't been discovered yet: it simply retries every 5 seconds until they're there. Each Bandwidth card gained a footer line, tested 07:16:50, next to any error, while the header keeps the relative "18s ago · next 9m".

13

How fast is the hop to the router?

how easy is a bandwidth test to router to add?
yes let's do that? It would be very helpful

A true throughput test to the router turned out not to be practical: both routers only serve a ~5 KB admin page, with no speed-test endpoint or iperf3, and hammering a router's web UI is the same kind of risk we'd already ruled out for the dish. But the OS already knows the answer to the useful question. CoreWLAN gives the Wi-Fi transmit rate, band, channel, width and signal, and the interface's ifi_baudrate gives the Ethernet speed. No packets needed, and it works inside the sandbox.

The first reading explained a mystery from earlier: the Mac's Wi-Fi was on 2.4 GHz, channel 11, 20 MHz wide, at ~137 Mbps, which is why the 5 Gb/s fibre kept measuring ~140 Mbps. Each panel header now carries a link chip (1 Gb/s on Ethernet, 137 Mbps · 2.4 GHz ch 11 · −65 dBm on Wi-Fi). It turns amber when Wi-Fi is on 2.4 GHz or the last download got within reach of the link rate, and hovering shows the Wi-Fi mode, noise and SNR. --selftest prints it too.

Where it stands

Phase 1 is complete and verified, and now watches every connection at once: each link (Ethernet → Starlink, Wi-Fi → fibre, …) gets its own stacked panel with interface-pinned probes and a download/upload bandwidth test every 10 minutes. The Router target follows each link's gateway, the Starlink dish is an optional target that's omitted when it's not there, live stats carry an ICMP/TCP method badge, and a 60 fps aurora ribbon scrolls smoothly through time in a resizable frameless window. The original Phase 2 — rich Starlink dish telemetry over the dish gRPC API — was shelved by choice: poking that API appears able to crash the dish, and the endpoint that serves telemetry also accepts reboot/stow, so NetHealth stays a passive latency monitor that never speaks to the dish's API.
